Yes — this is the right instinct, and it's worth being precise about what "SDK" means here, because it changes a few things on disk and forces a couple of design decisions you'd otherwise drift into.

The rule, stated cleanly

ttasks may be imported by anything. ttasks imports nothing from kanban. If you ever feel ttasks "needs to know" about JSON, HTTP, SSE, CSS, or a column name, that's the signal you've drawn the line in the wrong place.

A good smoke test: git grep -iE 'kanban|http|json|sse' ttasks/ should be empty, forever.

What that means concretely

ttasks/ is a Python package, not three loose modules. Move task.py, ledger.py, executor.py under ttasks/ with an __init__.py that exports the public surface (Task, TaskStatus, TaskType, TaskLedger, TaskExecutor, TaskResult, TaskContext, TaskCancelled, default_executor). That's the SDK's API contract. Anything not re-exported is private — including helpers like _run_command.

The board lives next to it, not inside it. Something like:

ttasks/        ← the SDK
  __init__.py
  task.py
  ledger.py
  executor.py
kanban/        ← one consumer of the SDK
  server.py
  adapter.py   ← JSON shaping lives here
  index.html
tests/         ← still tests the SDK only; board gets its own tests later
main.py        ← entry point that starts the kanban
demo.py        ← the current main.py, renamed; second consumer, proves the SDK works headless

Two consumers (demo.py and kanban/) is healthier than one — it stops the SDK from quietly growing board-shaped knobs.

The interesting question: where do the new capabilities live?

The board needs three things that don't exist yet: async submission, an event stream, and a way to render snapshots. Each one is a "which side of the line?" call.

1. Async submission / worker pool — SDK

Tempting to put threads in the board. Don't. "Run this task whenever you can" is a task-runner verb; a future CLI or TUI would re-implement the same pool. I'd add a small TaskRunner to the SDK that composes a ledger + executor + worker pool and exposes submit(task), cancel(task_id), etc. The board holds one TaskRunner. That's its entire handle into ttasks.

2. Event stream — SDK, in domain terms only

The board needs to know when a task transitions so it can push SSE. But the SDK must not know what SSE is. The right shape:

runner.subscribe(callback)   # callback(event: TaskEvent)
# TaskEvent: task_id, old_status, new_status, at

The board's SSE endpoint subscribes and re-broadcasts in its own format. Tests can subscribe to assert. A future TUI subscribes the same way. This is gap #2 from todo.html — and notice the board's existence is what justifies adding it. That's the healthy direction of pressure: the consumer pulls capabilities into the SDK, never the reverse.

3. Snapshotting / serialization — board

This is where people accidentally couple. Tempting to add Task.to_dict(). Don't — that's a JSON-flavored method on a domain object, and JSON is a board concern. Keep Task a plain dataclass with properties; let kanban/adapter.py own task_to_dict(task) -> {...}. If a future consumer wants protobuf or msgpack, ttasks doesn't care.

A couple of subtler calls

  • Columns are a board concept, not a domain concept. The SDK has 5 statuses. The board chooses to render them as 5 columns. A future TUI might show a flat list with status badges; that's its call. No COLUMN_ORDER constant in ttasks.
  • Filtering by status — the board can filter in Python via [t for t in ledger if t.status == ...]. Don't add ledger.by_status() until a second consumer wants it. YAGNI keeps the surface honest.
  • Persistence, when you tackle it later, is SDK. A PersistentTaskLedger or a pluggable storage backend belongs behind the ledger interface. The board shouldn't be able to tell whether the ledger is in-memory or on disk.
  • Drag-to-cancel from a terminal state. Your state machine forbids DONE → CANCELLED. The board has to honor that — the UI should refuse the drag, not the server should silently swallow a ValueError. The SDK's strictness is a feature; the board adapts to it.

What I'd build first

Smallest thing that makes the SDK / consumer split real and exercises the metaphor:

  1. Package move (ttasks/), demo.py rename, public API pinned in __init__.py.
  2. Add TaskRunner to the SDK (ledger + executor + thread pool + submit/cancel/subscribe).
  3. kanban/server.py with the v1 routes we already agreed on, polling-based, light theme. No SSE yet.
  4. main.py = "start the kanban on 127.0.0.1:8000."

Then SSE as a deliberate v2 — it's a one-liner once runner.subscribe exists.
