Looking at it as a task runner (rather than an experiment), here are the capability gaps I'd flag — grouped so you can decide which are in-scope vs deliberately out-of-scope.

Scheduling & concurrency (you said concurrency is intent)

  • Submit-and-forget: today execute() is synchronous and blocks the caller; there's no "enqueue this, run it when you can" verb.
  • Concurrency limits: no notion of "run at most N at once," per-type pools, or fairness between task types.
  • Queueing & prioritization: no ordering policy — FIFO, priority, due-time, etc.
  • Scheduled / delayed / recurring tasks: no "run at 3am" or "run every 5 minutes."
  • Dependencies between tasks: no "B runs after A succeeds," no fan-out/fan-in.
  • Backpressure: no signal when the system is saturated.

Reliability

  • Automatic retries with backoff — FAILED → RUNNING is allowed in the state machine but nothing drives it.
  • Crash recovery: if the process dies mid-task, the task is silently lost (tied to your persistence question).
  • At-least-once vs at-most-once semantics: undefined. Important once you have persistence + retries.
  • Heartbeats / stuck-task detection: nothing notices a handler that hangs without a timeout.
  • Graceful shutdown / drain: no way to say "stop accepting new work, let running tasks finish."

Observability

  • Streaming / incremental output: stdout/stderr are only available after the task ends. For long shell jobs that's painful.
  • Logs and history per task beyond a single error string and final output.
  • Progress reporting from handlers (percent, stage, custom messages).
  • Timing data: started-at, finished-at, duration. Only created_at exists today.
  • Metrics / counters: throughput, failure rate, queue depth.
  • Event stream / subscriptions: ability for an external watcher to be notified of state changes (status changed, task finished). This will matter a lot whichever external interface you pick.

Querying the ledger

  • Filter / search: today you can iterate, get-by-id, or check membership. No "list all FAILED," "find by title," "tasks created in the last hour."
  • Pagination / counts by status.
  • Bulk operations: cancel-all-pending, retry-all-failed.

Inputs & outputs

  • Structured inputs: payload is a single string. No parameters, env vars, working directory, stdin, secrets, files.
  • Structured outputs / artifacts: no concept of a result document, file output, or typed return.
  • Result size limits: a chatty shell command will pile output into memory unbounded.
  • Passing results between tasks (needed once dependencies exist).

Security & multi-tenancy

  • Identity / ownership: who created the task, who may cancel it.
  • Authorization: today anyone with a reference can cancel/delete anything.
  • Sandboxing / resource limits: CPU, memory, disk, network for shell tasks.
  • Audit log: who did what, when.
  • Secret handling: payloads are plain strings; no redaction in logs/output.

Lifecycle gaps in the current model

  • Paused / suspended state — useful for maintenance windows or manual gating.
  • Expired / timed-out as a distinct terminal state vs being folded into FAILED (you may or may not want this — worth a deliberate choice).
  • Retention policy: when do DONE/CANCELLED tasks leave the ledger? Today: never, unless someone deletes them.
  • Updating a task after creation (e.g., bumping a timeout, editing payload before run) — currently impossible by design; confirm that's intentional.

Handler ergonomics (relevant once prompt/agent land)

  • Async handlers: handler signature is sync; a prompt/LLM handler is naturally async and long-lived.
  • Cancellation cooperation contract: shell tasks are killed via the OS; in-process handlers (prompt/agent) need a documented "check cancellation here" pattern. The hook exists (raise_if_cancelled) but there's no contract that handlers must poll it.
  • Per-handler configuration: e.g., prompt backend choice, agent tools — no place to put it.

My short list if you want to prioritize

If this is a task runner and not just a state machine demo, the three I'd pick up first — because everything else assumes them — are:

  1. Async submission + a worker pool (turns this from a library into a runner).
  2. An event/subscription stream for status changes (unblocks any external interface — CLI, HTTP, TUI — without committing to one yet).
  3. Streaming output + timing metadata on tasks (cheap, and the lack of it will bite the moment you actually use this).

Persistence and the external interface can wait behind those, and the answers to those two questions will be easier once 1–3 exist.

User API improvements

A separate track from the capability gaps above: how the library feels to a consumer once you import it. Ordered roughly by impact-per-line-of-change. Some items have shipped; others are deferred or dropped after deliberate decisions.

Shipped

Results on the Task

Status: done (commit 0fe7e3b).

Task now carries task.result: TaskResult | None, populated by TaskExecutor.execute() on every terminal path — success, failure, and cancellation. Previously only the success path produced a TaskResult; failure and cancellation lost stderr/returncode inside the raised exception. That asymmetry is closed.

Practical payoff: the ledger is the single post-run view. Consumers walk graph.ledger and read task.status, task.result.output, task.result.error without touching Future, .result(), .exception(), or id-keyed dicts. Futures remain available as an escape hatch from graph.run() for power users.

Structural: TaskResult moved from executor.py into task.py so the domain types live together. task.py uses from __future__ import annotations so the forward reference Task.result -> TaskResult reads without quotes.

Package layout: ttasks/ with re-exports

Status: done.

The repo moved from a flat layout (sibling task.py, executor.py, ledger.py, workflow.py at the root) to a src/ttasks/ package with an __init__.py that re-exports the public surface. Consumers now use a single import line:

from ttasks import Task, TaskType, TaskGraph, default_executor

Submodule imports (from ttasks.executor import …) still work for callers who want to be explicit; the existing tests use that form, while consumers and main.py use the flat surface.

Decisions made along the way:

  • Layout: src/ layout (src/ttasks/…) rather than flat, to keep the build / install path honest if PyPI ever happens.
  • Build backend: hatchling, declared in pyproject.toml. uv build now produces a wheel without extra config.
  • TaskGraph location: stays inside the package as ttasks.workflow rather than being split into a separate distribution. The SDK-vs-consumer distinction is preserved at the submodule level, not the install level. One pip install ttasks, one library.
  • Internal imports: relative (from .task import …) inside the package. Idiomatic and survives a future rename of the package.
  • Public surface: 10 names exported — Task, TaskStatus, TaskType, TaskResult, TaskLedger, TaskExecutor, TaskContext, TaskCancelled, default_executor, TaskGraph. Nothing trimmed; handler authors get TaskContext from the top level without having to know about ttasks.executor.
  • Public-API contract test: tests/test_public_api.py pins __all__ against an expected set, checks every name resolves, and asserts identity against the canonical submodule object. Adding or removing a public name without updating the contract fails immediately.
  • PyPI publication: not a current goal, but the structure is ready. Future work: package description, classifiers, README polish.

Coverage moved from four per-module --cov= targets to a single --cov=ttasks; 103 tests, 100% coverage across __init__.py, task.py, executor.py, ledger.py, workflow.py.

Open

GraphRun return type from graph.run()

Status: open. Less urgent after results-on-Task landed.

Original motivation: graph.run() returns dict[str, Future], which is too raw for ordinary consumers. A structured GraphRun would expose .succeeded, .failed, .blocked lists and treat the futures dict as an escape hatch.

Why it's less urgent now: with task.result on every task, walking the ledger already gives you these views:

succeeded = [t for t in graph.ledger if t.status == TaskStatus.DONE]
failed    = [t for t in graph.ledger if t.status == TaskStatus.FAILED]
blocked   = [t for t in graph.ledger if t.result is None and t in graph]

GraphRun would mainly be sugar over these filters. Worth doing eventually as ergonomic polish; not a behavioural gap.

default_executor() naming and role

Status: open. Marginal.

The name reads as “the default” but it's a factory function returning a fresh executor each call. Minor consequences: no clear convention for whether consumers should cache the returned executor or call the factory per graph.run(); configuring handlers (prompt, agent) has to happen on each returned instance.

Possible moves: rename to new_executor() / build_executor(); or make it a module-level singleton; or have graph.run() default the executor internally (rejected — hides a dependency). Defer until something else makes the choice necessary.

Considered and dropped

Task.bash(...) classmethod constructor

Proposed: Task.bash("A", "echo hi") as a shorthand for Task(title="A", type=TaskType.BASH, payload="echo hi"). Dropped by deliberate decision — explicit type= stays.

graph[a] = None shorthand for root tasks

Proposed: allow None in place of [] for tasks with no dependencies. Dropped — the empty list is honest about meaning “no deps” and is consistent with non-root assignments.
