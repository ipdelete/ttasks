Looking at it as a task runner (rather than an experiment), here are the capability gaps I'd flag — grouped so you can decide which are in-scope vs deliberately out-of-scope.

Scheduling & concurrency (you said concurrency is intent)

  • Submit-and-forget: today execute() is synchronous and blocks the caller; there's no "enqueue this, run it when you can" verb.
  • Concurrency limits: no notion of "run at most N at once," per-type pools, or fairness between task types.
  • Queueing & prioritization: no ordering policy — FIFO, priority, due-time, etc.
  • Scheduled / delayed / recurring tasks: no "run at 3am" or "run every 5 minutes."
  • Dependencies between tasks: no "B runs after A succeeds," no fan-out/fan-in.
  • Backpressure: no signal when the system is saturated.

Reliability

  • Automatic retries with backoff — FAILED → RUNNING is allowed in the state machine but nothing drives it.
  • Crash recovery: if the process dies mid-task, the task is silently lost (tied to your persistence question).
  • At-least-once vs at-most-once semantics: undefined. Important once you have persistence + retries.
  • Heartbeats / stuck-task detection: nothing notices a handler that hangs without a timeout.
  • Graceful shutdown / drain: no way to say "stop accepting new work, let running tasks finish."

Observability

  • Streaming / incremental output: stdout/stderr are only available after the task ends. For long shell jobs that's painful.
  • Logs and history per task beyond a single error string and final output.
  • Progress reporting from handlers (percent, stage, custom messages).
  • Timing data: started-at, finished-at, duration. Only created_at exists today.
  • Metrics / counters: throughput, failure rate, queue depth.
  • Event stream / subscriptions: ability for an external watcher to be notified of state changes (status changed, task finished). This will matter a lot whichever external interface you pick.

Querying the ledger

  • Filter / search: today you can iterate, get-by-id, or check membership. No "list all FAILED," "find by title," "tasks created in the last hour."
  • Pagination / counts by status.
  • Bulk operations: cancel-all-pending, retry-all-failed.

Inputs & outputs

  • Structured inputs: payload is a single string. No parameters, env vars, working directory, stdin, secrets, files.
  • Structured outputs / artifacts: no concept of a result document, file output, or typed return.
  • Result size limits: a chatty shell command will pile output into memory unbounded.
  • Passing results between tasks (needed once dependencies exist).

Security & multi-tenancy

  • Identity / ownership: who created the task, who may cancel it.
  • Authorization: today anyone with a reference can cancel/delete anything.
  • Sandboxing / resource limits: CPU, memory, disk, network for shell tasks.
  • Audit log: who did what, when.
  • Secret handling: payloads are plain strings; no redaction in logs/output.

Lifecycle gaps in the current model

  • Paused / suspended state — useful for maintenance windows or manual gating.
  • Expired / timed-out as a distinct terminal state vs being folded into FAILED (you may or may not want this — worth a deliberate choice).
  • Retention policy: when do DONE/CANCELLED tasks leave the ledger? Today: never, unless someone deletes them.
  • Updating a task after creation (e.g., bumping a timeout, editing payload before run) — currently impossible by design; confirm that's intentional.

Handler ergonomics (relevant once prompt/agent land)

  • Async handlers: handler signature is sync; a prompt/LLM handler is naturally async and long-lived.
  • Cancellation cooperation contract: shell tasks are killed via the OS; in-process handlers (prompt/agent) need a documented "check cancellation here" pattern. The hook exists (raise_if_cancelled) but there's no contract that handlers must poll it.
  • Per-handler configuration: e.g., prompt backend choice, agent tools — no place to put it.

My short list if you want to prioritize

If this is a task runner and not just a state machine demo, the three I'd pick up first — because everything else assumes them — are:

  1. Async submission + a worker pool (turns this from a library into a runner).
  2. An event/subscription stream for status changes (unblocks any external interface — CLI, HTTP, TUI — without committing to one yet).
  3. Streaming output + timing metadata on tasks (cheap, and the lack of it will bite the moment you actually use this).

Persistence and the external interface can wait behind those, and the answers to those two questions will be easier once 1–3 exist.
