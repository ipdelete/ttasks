ttasks roadmap

Read top-down. Items are ordered by priority, not by category. The first three tiers are the work plan; the user-API improvements section at the bottom is a closed track kept for reference.

Last reviewed after commit f4565c5. Tier ordering reflects what unblocks what, cost-per-value, and what makes the library useful for the next plausible consumer.

Tier 1 — do now (in this order)

1. Timing on TaskResult

~1 hour. No design questions.

Add started_at, finished_at, duration to TaskResult; populate in TaskExecutor.execute() on every terminal path. Mechanical edits, ~3 new tests.

Why first: cheapest meaningful win on the list. Immediately useful in main.py output and any future UI. Finishing something small first re-grooves the TDD rhythm before committing to the bigger Tier-1 items. The natural home (TaskResult) already exists, so there's no “where does this live?” question.

2. Passing results between tasks

~3 hours. One real design question.

Inside B's handler there's no clean way to read A's output. A handler receives a TaskContext containing only task and a cancellation event — no view of upstream results. TaskGraph ships a DAG runner without a way to plumb data through it.

Design question: where do upstream results live? Two candidates:

  • TaskContext.upstream: dict[str, TaskResult], populated by the runner before dispatch. Handler reads ctx.upstream[parent_id].output. Runtime concern, runtime location.
  • Auto-injection into the task payload via templating. Task-definition concern, task-definition location.

I lean toward TaskContext — plumbing is runtime mechanics, not task identity. After this lands, DAGs stop being demos and become workflows.

3. Event stream / subscriptions

~5 hours. Real design.

The gateway. After graph.run() grew interesting mid-run behavior (multiple tasks transitioning, descendants getting blocked, parallel branches finishing at different moments), the only way to observe any of it is to wait for the blocking call to return. Once an event stream exists, streaming output, progress reporting, metrics, and any external interface (CLI, HTTP, TUI) all become viable without committing to one.

Probable shape: a small EventBus on TaskLedger or TaskExecutor with subscribe(callback); emit on every status transition. Real design question: filter language (by task id, by status, by graph?). I'd start with “everything, consumer filters” and add specifics on demand.

After Tier 1 the library goes from “good DAG runner” to “DAG runner you can build a real UI against.”

Tier 2 — do next

These either depend on Tier 1 or build naturally on it. Order within the tier is roughly cost-ascending.

4. Streaming output

~3 hours. Depends on the event stream.

Handlers emit chunks via the event bus instead of buffering until done. For long shell jobs that's the difference between “is it hung?” and a live tail. The event-bus dependency is hard — without it you'd need polling, which is the wrong shape.

5. Async submit-and-forget on the executor

~2 hours. Self-contained.

executor.execute(task) already covers the sync single-task case. What's missing is executor.submit(task) -> Future — submit, get a Future immediately, collect later. Today the workaround is wrapping a single task in a one-node TaskGraph, which works but is heavy.

Pool lifecycle is the only real design question: lazy creation on first submit(), explicit close(), or context-manager protocol? I lean lazy + explicit close + idempotent on __del__.

6. Single-task retry policy

~2 hours.

RetryPolicy(max_attempts, backoff) on the executor or per-task; FAILED → RUNNING is already allowed in the state machine, so nothing structural is in the way. Graph-level retry (rerun only the failed subgraph, unblock its descendants) is a richer feature and lives in Tier 3 — revisit once single-task retry exists and you've felt the gap.

7. Graceful drain / shutdown on the executor

~2 hours. Becomes needed once submit-and-forget exists.

“Stop accepting new work, let running tasks finish.” Once an executor owns a thread pool, callers need a way to wind it down without losing in-flight work.

8. Progress reporting from handlers

~1 hour. Depends on the event stream.

Handlers call ctx.emit_progress(percent, message); the event flows through the same bus. Cheap once Tier 1 is done.

Tier 3 — can wait until something forces the issue

Important but not urgent. Each entry is either blocked on a bigger decision, defensive against a problem that hasn't bitten yet, or sugar over a workaround that's currently fine.

  • Persistence / crash recovery. Big decision (sqlite vs JSON vs pluggable). Affects everything downstream. Don't pick a shape until the consuming app forces one.
  • Graph-level retry (rerun the failed subgraph). Genuinely useful but real design work; revisit after single-task retry lands.
  • Scheduled / delayed / recurring tasks. Big surface area. Only worth it if this runs as a long-lived service.
  • Structured inputs (env, cwd, stdin, secrets, files). Touches the Task dataclass. You'll feel the pain the moment you write a real bash task that needs PWD — add then.
  • Structured outputs / artifacts. TaskResult.raw is object, which is permissive but not typed; revisit when a consumer wants typed returns.
  • Result size limits. Defensive. You'll hit it once a chatty subprocess fills memory.
  • Heartbeats / stuck-task detection. Requires a timeout model first.
  • Paused / suspended state. Only matters with a service or scheduler.
  • Expired-as-distinct-terminal-state (vs folded into FAILED). Cheap once you decide; not blocking anything.
  • Retention policy. When do DONE/CANCELLED tasks leave the ledger? Becomes pointed only after persistence lands. With shared ledgers, eviction needs to know whether any graph still references the task.
  • Bulk ledger ops (cancel_all_pending, retry_all_failed). Sugar over comprehensions; add when somebody asks.
  • Ledger-level filtering [position]: intentionally left to consumer comprehensions ([t for t in ledger if t.status == TaskStatus.FAILED]). The asymmetry with graph.succeeded/failed/blocked reflects the layering — graphs report on their slice, the ledger is just storage.
  • Updating a task after creation [position]: the runner mutates task.status and task.result during execution; callers do not mutate tasks after construction. “Immutable Task” is the caller-side contract, not a hard invariant. Worth restating in the README.
  • Backpressure / global concurrency caps / per-type pools / queueing & prioritization. Matter at scale; graph.run(max_workers=N) is enough for now.
  • At-least-once vs at-most-once semantics. Becomes important once persistence + retries exist.
  • System-wide metrics / counters. Per-graph counts already available via graph.succeeded/failed/blocked; system-wide waits for the event stream + a consumer that wants them.
  • Logs and history per task beyond a single error string. Will become natural once the event stream is in place — events are the history.

Tier 4 — probably out of scope for this library

Application concerns or future-service concerns. Revisit only if ttasks becomes a long-lived service rather than an in-process library.

  • Identity / ownership / authorization / audit log / secret handling. Consumer's responsibility while we're an in-process library.
  • Sandboxing / resource limits (CPU, memory, disk, network for shell tasks). Same.
  • Async handlers. Will become natural when prompt/agent handlers exist; design the contract then.
  • Per-handler configuration. Same. The current make_default_executor() + .register() pattern suffices.
  • Cancellation cooperation contract for in-process handlers. Document when prompt/agent land; nothing to enforce until then.

Already shipped (capability)

  • Dependencies between tasks. Addressed by TaskGraph in ttasks.workflow. Fan-out, fan-in, diamonds, halt-on-failure with blocked-descendant propagation.
  • Per-graph counts & filtering. graph.succeeded, graph.failed, graph.blocked, graph.ok as properties; graph.roots(), graph.leaves() as methods.
  • Sync single-task execution. executor.execute(task) runs one task, sets task.result, returns the TaskResult.
  • Per-graph concurrency knob. graph.run(max_workers=N).

See the user-API improvements section below for the API-shape work that shipped alongside.

User API improvements

A separate track from the capability gaps above: how the library feels to a consumer once you import it. Ordered roughly by impact-per-line-of-change. Some items have shipped; others are deferred or dropped after deliberate decisions.

Shipped

Results on the Task

Status: done (commit 0fe7e3b).

Task now carries task.result: TaskResult | None, populated by TaskExecutor.execute() on every terminal path — success, failure, and cancellation. Previously only the success path produced a TaskResult; failure and cancellation lost stderr/returncode inside the raised exception. That asymmetry is closed.

Practical payoff: the ledger is the single post-run view. Consumers walk graph.ledger and read task.status, task.result.output, task.result.error without touching Future, .result(), .exception(), or id-keyed dicts. Futures remain available as an escape hatch from graph.run() for power users.

Structural: TaskResult moved from executor.py into task.py so the domain types live together. task.py uses from __future__ import annotations so the forward reference Task.result -> TaskResult reads without quotes.

Package layout: ttasks/ with re-exports

Status: done.

The repo moved from a flat layout (sibling task.py, executor.py, ledger.py, workflow.py at the root) to a src/ttasks/ package with an __init__.py that re-exports the public surface. Consumers now use a single import line:

from ttasks import Task, TaskType, TaskGraph, make_default_executor

Submodule imports (from ttasks.executor import …) still work for callers who want to be explicit; the existing tests use that form, while consumers and main.py use the flat surface.

Decisions made along the way:

  • Layout: src/ layout (src/ttasks/…) rather than flat, to keep the build / install path honest if PyPI ever happens.
  • Build backend: hatchling, declared in pyproject.toml. uv build now produces a wheel without extra config.
  • TaskGraph location: stays inside the package as ttasks.workflow rather than being split into a separate distribution. The SDK-vs-consumer distinction is preserved at the submodule level, not the install level. One pip install ttasks, one library.
  • Internal imports: relative (from .task import …) inside the package. Idiomatic and survives a future rename of the package.
  • Public surface: 10 names exported — Task, TaskStatus, TaskType, TaskResult, TaskLedger, TaskExecutor, TaskContext, TaskCancelled, make_default_executor, TaskGraph. Nothing trimmed; handler authors get TaskContext from the top level without having to know about ttasks.executor.
  • Public-API contract test: tests/test_public_api.py pins __all__ against an expected set, checks every name resolves, and asserts identity against the canonical submodule object. Adding or removing a public name without updating the contract fails immediately.
  • PyPI publication: not a current goal, but the structure is ready. Future work: package description, classifiers, README polish.

Coverage moved from four per-module --cov= targets to a single --cov=ttasks; 103 tests, 100% coverage across __init__.py, task.py, executor.py, ledger.py, workflow.py.

Graph as its own result type (originally: GraphRun return)

Status: done. Shipped with a different shape than originally proposed.

Original motivation: graph.run() returned dict[str, Future], which leaked concurrent.futures mechanics into every consumer. The original proposal was a separate frozen GraphRun dataclass with succeeded, failed, blocked fields and a futures escape hatch.

What actually shipped, after pushback on duplication:

  • run() returns self. The graph itself is the navigable result. No new class. No snapshot lists to keep in sync with the ledger.
  • Status views as properties on TaskGraph: graph.succeeded, graph.failed, graph.blocked, graph.ok. Each is a live filter over the graph's own tasks — not a captured copy. Calling them before run() returns honest empty lists / False.
  • Topology methods on TaskGraph: graph.roots() and graph.leaves(). Tangential to the run-state question, but they complete the introspection story.
  • Explicit _blocked tracking. The graph remembers which task ids were skipped during the most recent run() in a private set; graph.blocked reads it directly. This makes “blocked by upstream failure” cleanly distinct from “PENDING because nobody called run() yet”. The set is cleared at the start of every run().
  • Futures dict removed entirely. It was unused in production code (main.py already walked the ledger) and load-bearing only in tests. Six test assertions rewritten onto task.status / graph.failed / graph.blocked; the dict is now purely internal state inside run().

Decisions made along the way:

  • Properties for status, methods for topology. “What's the state of this graph?” reads as an attribute (no parens); “compute X about this graph's shape” reads as a query (parens). Both happen to be computed; the distinction is about how callers think about them.
  • blocked tracked explicitly rather than derived from task.result is None. The two states aren't the same: a PENDING task in an unrun graph is different from one actively skipped because its parent failed. The runner already had the blocked set in its closure; we just retained it.
  • No new public exports. Everything is on TaskGraph directly, so ttasks.__all__ stays at 10 names. The public-API contract test required no update.
  • Status views iterate self, not self._ledger. In a multi-graph setup with a shared ledger, each graph reports on its own slice. A task that lives in another graph sharing the same ledger is correctly excluded.
  • ok = “every task in the graph succeeded”, not “no failures and no blocked”. An empty graph is vacuously ok; an unrun graph with PENDING tasks is not ok. Subtle but matches what the word means.

Tests: 22 new tests covering run() return identity, the four status properties (before run, after clean run, after failure, after blocking), and the two topology methods. Six existing futures-based tests rewritten. main.py rewritten to demo three graphs (linear, diamond, failing) against a shared ledger and show off the new graph-level reporting. 125 tests pass, 100% coverage across the package.

Executor factory naming: default_executor() → make_default_executor()

Status: done.

The original name read as “the default” — implying a singleton — but the function returned a fresh TaskExecutor on every call. Subtle gotcha: a caller who did e = default_executor(); e.register(MY_TYPE, my_handler) would find that the registration only applied to e, not to any other call site, because each call built a new instance.

Renamed to make_default_executor(). The make_ verb prefix matches the Python convention for “build me an X with sensible defaults” (cf. dataclasses.make_dataclass) and removes the singleton implication. The default qualifier earns its place by distinguishing “the one with the built-in handlers pre-registered” from any future bare or alternative constructor.

The docstring now spells out what was previously implicit:

  • Returns a fresh instance on every call — not a cached singleton.
  • BASH, POWERSHELL, PROMPT, and AGENT handlers are pre-registered.
  • PROMPT and AGENT are currently stubs that raise NotImplementedError.
  • Customization happens by calling .register() on the returned instance and is local to that instance.

Options considered and rejected:

  • Make TaskExecutor() pre-wired (and drop the factory): couples the executor class to specific built-in handlers; loses the “executor is generic, handlers are pluggable” story.
  • Real module-level singleton: global mutable state, test pollution across handler registrations.
  • Auto-build inside graph.run(): hides where handler configuration happens; makes that config harder to discover.
  • Literal default_executor_factory(): matches the user request more directly but reads as Java-ish in Python; make_ carries factory semantics idiomatically.

No deprecation alias — internal repo, no external consumers. All call sites (main.py, ~3 test files, __init__.py re-export, public-API contract test) updated in one pass. Public surface stays at 10 names; only one was renamed. 125 tests pass, 100% coverage.

Considered and dropped

Task.bash(...) classmethod constructor

Proposed: Task.bash("A", "echo hi") as a shorthand for Task(title="A", type=TaskType.BASH, payload="echo hi"). Dropped by deliberate decision — explicit type= stays.

graph[a] = None shorthand for root tasks

Proposed: allow None in place of [] for tasks with no dependencies. Dropped — the empty list is honest about meaning “no deps” and is consistent with non-root assignments.
